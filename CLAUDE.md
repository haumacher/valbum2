# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VAlbum2 — a self-hosted photo/video album. A Java backend (Jetty) serves albums read from a folder tree as a JSON API; it never modifies or deletes the original photos (all edits are stored in sidecar files; the only file operations on originals are same-filesystem renames — the explicit library migration and the album move of #47, which sets duplicates aside in `.valbum/duplicates/`). The only front end is the Flutter app in **`valbum_ui/`** (web, mobile, desktop). The former GWT web client was removed in ROADMAP Phase 0.

Direction, phases and decisions are recorded in `ROADMAP.md`.

## Two separate toolchains

This repo mixes **Maven** (Java backend, multi-module: `image-server`, `image-server-shared`, `util-servlet`) and **Flutter/Dart** (`valbum_ui/`), with independent dependency management. A full build means running both.

### Maven (backend)

- Build everything: `mvn clean install` (run from repo root)
- Run the demo server: `mvn exec:java@test-server -pl :image-server` → http://localhost:9090/valbum/ (port 9090, non-standard)
- Run the packaged jar: `java -jar image-server/target/image-server-jar-with-dependencies.jar --basepath /path/to/photos [--port 8080] [--contextpath valbum] [--webroot /path/to/flutter/build/web] [--auth off|writes|all] [--pairing-secret <secret>] [--invite admin|members] [--preview-threads <n>] [--migrate-to-user <name>]`
- Authentication and permissions (#28, #45, #82, #83): `--auth` (`off|writes|all`) says what an anonymous caller may do; a device pairs with `POST <data>/?action=pair` against the pairing secret (printed at start-up, `demo` for the demo server) and then sends `Authorization: Bearer <token>`. **A space is the unit of everything**: one server hosts one space (the base folder, today's addresses) or several (#82). A user belongs to exactly one space, lives in that space's `<space>/.valbum/users.json` with their devices, and holds **one permission for the whole space**: `{role: admin|edit|contribute|view, clearance: public|nonPrivate|all, mayShare: bool}` (#83). `AuthService.rights(caller, path)` answers from the role alone and the same for every path — admin/edit → view+download+contribute+edit, contribute → view+download+contribute, view → view+download; a share link answers what the link itself was created with; an anonymous caller answers view+download where the space is open (`--auth writes`, or `space.json` `anonymous: public`) and nothing otherwise. `AuthService.clearance(...)` answers the stored clearance (admin: everything; anonymous: public), `?viewAs=public|members` lowers one's own for a request, and `PrivacyFilter` drops what is above it on the way out (`ImagePart.privacy` 0..2, cache and sidecars untouched). Every endpoint asks those two: listing/thumbnail → `view`, original → `download`, sidecar PUT / move source / `?action=place` → `edit`, upload / `?action=check` / move target / album creation → `contribute`. `Roles.of` reads the older names of a library written before #83 (`member` → edit/all/share, `guest` → view/nonPrivate/no-share) without rewriting the file, and the protocol answers the new names. Management (admin only): `GET <data>/?type=users` (role, clearance, mayShare, devices), `POST <data>/?action=invite|uninvite` (the invitation carries role/clearance/mayShare, capped at the inviter's), `?action=set-permission` (`UserPermission{name, role, clearance, mayShare}`; the last admin is never demoted, 409 `LAST_ADMIN`), `?action=remove-user` (`MemberName`; their devices go, their photos and their attribution stay). **Retired by #83, answering 410 with an `ErrorInfo` naming the replacement for one release**: `?type=grants|groups|links`, `?action=grant|revoke|group|ungroup|regroup|unlink|promote` — grants, groups, materialised links, guest roots and the `~<owner>/` path form are gone, with their stores (`GrantStore`, `GroupStore`, `Subjects`, `links/*`). Moving (#47): `POST <folder>/?action=move` with a `MoveRequest` answers a `MoveResult` per name; `MoveService` renames only, carries the `ImagePart` and its `.hashes.json` entry along, sets duplicates aside; a move out of an album needs `edit` or the caller as contributor of every named image (`CONTRIBUTION_REFUSED`). Share links (#51, #84): `POST <folder>/?action=share` with a `ShareLink` (label, expires, maxPrivacy, minRating, rights) needs the **share flag** (`AuthService.mayShareLinks`, else 403 `SHARING_REFUSED`); `edit` in the rights is 400 `SHARE_EDIT_REFUSED` and a `maxPrivacy` above the creator's own clearance is 400 `shareAboveClearance(...)` — **refused, never quietly trimmed**, so nobody hands out a link they believe shows less than it does. What the link may do and show is written on it (`{id, tokenHash, owner, path, rights, maxPrivacy, minRating, createdBy, created, revoked}` in `<space>/.valbum/shares.json`) and **frozen there**: a later change to its maker's permission neither widens nor narrows it. **The link is the permission — there is no grant beside it.** The answer is `ShareLinkCreated` (token once, `url` = `<context>[/<space>]/s/<token>/`). A share bearer's `/` is the shared folder (outside → 404 `SHARE_CONFINED`), it reads even where the space refuses anonymous callers, contributes only with `contribute` and is attributed `token:<id>`, clearance `min(MEMBERS, maxPrivacy)` (a link never shows a private image, whoever made it), parts below `minRating` dropped, expired/revoked → 410 on **every** endpoint including thumbnails and renditions, `AuthInfo.share` set for link callers only; a token of another space is simply unknown there. Management: `GET <folder>/?type=shares` and `POST ?action=unshare` show and withdraw **one's own** links, an administrator's every link of the space (`ImageServlet.mine`; a link of somebody else's is answered `SHARE_UNKNOWN`, never "whose"); `?action=remove-user` withdraws every link the removed user handed out and says how many in `UserList.revokedLinks`. Invitations (#52): `POST <data>/?action=invite` records `{id, tokenHash, role, clearance, mayShare, invitedBy, note, expires, used, …}` in `<space>/.valbum/invitations.json` and answers a URL `<context>[/<space>]/i/<token>/`; accepting is pairing (`PairRequest.invitation` + a free `userName`) and creates the user with the invitation's permission; an invitation bearer is anonymous everywhere but `?type=auth`, which answers `AuthInfo.invitation`. Device codes (#65): `POST <data>/?action=device-code` answers `DeviceCodeCreated{code, expires}` (eight characters of `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, ten minutes, once) stored hashed in `<space>/.valbum/device-codes.json`; it is never a bearer and never a URL, only `PairRequest.deviceCode`, and it dies with the device that issued it (`DEVICE_CODE_ISSUER_GONE`). Devices: `GET <data>/?type=devices` answers one's **own** devices, `POST ?action=unpair` removes one of one's own (and revokes the codes it handed out). Token lookup: devices, then shares, then invitations. `GET <data>/?type=auth` reports mode, device, user, **role, clearance, mayShare**, space, and the share or invitation a token opened. Every JSON answer carries `Cache-Control: no-store` and `Vary: Authorization` (`ImageServlet.allowCrossOrigin`). Attribution (#53): `.hashes.json` entries carry `contributor` (`user:<name>`, `token:<id>`, `anonymous`) and `contributorLabel`, derived onto `ImagePart.contributor`/`contributorLabel` on read and cleared before any sidecar write. Cameras (#78): `ImagePart.camera` is `ImageData.cameraLabel(make, model)` from the EXIF `Make`/`Model` (both trimmed, blanks collapsed, joined with one blank, the make left out when the model already begins with it as a whole word ignoring case), stored in the sidecar like `date`. Video dates (#72): a video is dated by the `mvhd` creation time of its container, and a time before `ImageData.EARLIEST_RECORDING` (1990-01-01 UTC) is no recording time, so the file's modification time stands; `AlbumUtil.insertSorted` never resorts what a sidecar already lists. Dates and placement (#48): `AlbumInfo.date` is stored, `effectiveDate` is derived on read by `AlbumDate` (explicit → folder-name date → earliest image date) and cleared before any sidecar write; `ListingInfo.placement` (`NONE|BY_YEAR|BY_YEAR_MONTH`) is applied by `PlacementRule` on creation, on a move into the folder, and by `POST <folder>/?action=place`.
- Spaces (#82, Phase 6): a server hosts one space or several. `Spaces.detect` decides the mode at start-up — **multi** as soon as one folder directly below the base folder carries `.valbum/space.json`, **single** otherwise; `--spaces auto|single|multi` overrides. `SpaceStore` reads `space.json` `{name, anonymous: none|public}` (missing/unknown values read closed); a space is created on disk by hand, never by the server, and a new one is picked up by a restart. Each space has its **own** `AuthService` rooted at its own folder, so its `.valbum/users.json`, devices, invitations and albums are its own and a token of space A is simply unknown in space B (anonymous there). Anonymous access is a property of the space: `public` → the space runs like `--auth writes`, `none` → like `--auth all`; a server-wide `--auth all` is never loosened and `--auth off` stays off. Addressing in multi mode goes through `SpaceServlet` at the context root: `<context>/<space>/data/...` is that space's data root (the request is handed on with servlet path `/<space>/data`, so redirects, `Location.spell` and share URLs are spelled in the caller's coordinates), `<context>/<space>/` serves the app with `<base href>` rebased onto it (`ResourceServlet.setBaseSegments` + `WebRootResolver.singleSegmentBase`, the one-segment sibling of `/s/<token>/`), the app's own files are untouched; a session of a space lives **under** it — `<context>/<space>/s/<token>/` and `<context>/<space>/i/<token>/`, rebased by `WebRootResolver.spaceSessionBase` (the three-segment sibling of `/s/<token>/`), because the app opened there has to find a data root, and `ImageServlet.appUrl` derives that base from the request's own servlet path so a single-space server keeps spelling `<context>/s/<token>/` exactly as before; a session address at the context root of a multi-space server is refused with `SpaceServlet.sessionNeedsSpace`, and a first segment that is neither a space nor a file is answered `404` with an `ErrorInfo` (`SpaceServlet.noSuchSpace`). Single mode keeps every address it had. Bootstrap: the server-wide pairing secret makes the **first admin of a space** and afterwards only adds devices of that same admin — a stranger is told apart by the `userName` (`UserStore.nameOwner`). A pairing that would *create* the admin refuses a blank `userName` with 400 `ADMIN_NAME_REQUIRED` (#86): in a space the administrator is one user among several, and their name is what the users list shows, what an attribution records and what `set-permission`/`remove-user` address them by. A **nameless** admin can only come from a library written before Phase 6; adding a device to them still works with no name, and `AuthService.nameNamelessOwner(suggestion)` gives them one once — at start-up (`Main.reportSpace`, one printed line) or by `--migrate-to-spaces` (a report line) — the space's segment in multi mode, `owner` in single mode, with `-2`, `-3`… when a user or a top-level folder already holds it, and their devices and token hashes untouched, so every device keeps working. So a signed-in user always has a name and `Caller.subject()` never files their contribution as `anonymous`; every further user comes in through an invitation, which now carries `role`, `clearance` and `mayShare` (`Clearances` = `public|nonPrivate|all`, capped at the inviter's own), stored on the created user. `ImagePart`-style permission fields on the stored user (`clearance`, `mayShare` in `users.json`) and on `AuthInfo`/`UserEntry`/`Invitation` are written and answered here and enforced by #83. `?type=auth` names the space, the role, the clearance and the share flag. Migration is explicit: `--migrate-to-spaces` (like `--migrate-to-user`, refuses to start the server, rename-only, nothing deleted) turns an un-migrated library into the one space it already is (nothing moves) and a per-user library into a multi-space server — every user folder gets a `space.json` and a `users.json` holding that user as its admin with their devices, and `users.json`/`grants.json`/`groups.json`/`shares.json`/`invitations.json`/`device-codes.json`/`.valbum/guests/` plus every `.links.json` and `share-registry.json` in the tree are moved under `<base>/.valbum/retired/<timestamp>/` and named in a printed report saying what each held and what to do instead (`SpacesMigration`).
- Video renditions (#74): beside the poster frame, `VideoRenditions` (one per servlet, shut down in `ImageServlet.destroy()`) makes two sidecars per video in the album's `.vacache` — `video-<name>.mp4` (faststart, H.264 720 px short side, ≤30 fps, AAC) and `teaser-<name>.mp4` (~3 s from ~10 % in, silent, 240 px, faststart) — with the FFmpeg *program* of the bundled `org.bytedeco:ffmpeg` (`Loader.load(org.bytedeco.ffmpeg.ffmpeg.class)`), run as a child process with an argument list (never a command string), `-threads` at half the processors, one transcode at a time on a dedicated single-thread executor independent of the #69 preview permits. The encoder is chosen once by asking the program (`-encoders`): `libx264` if present, else `libopenh264` (what the LGPL build ships), else nothing is transcoded. `?type=video` / `?type=teaser` on an image path need `view` like the thumbnail and answer `video/mp4` over the existing range path; a rendition not yet made is never awaited — `202` + `ErrorInfo` `RENDITION_PENDING` + `Retry-After: 10` and the transcode is queued (deduplicated per rendition); a failed transcode is remembered for the process lifetime and answered `500` + `RENDITION_FAILED` with the FFmpeg tail in the log. Written to `.tmp` and moved atomically, invalidated like previews (`PreviewCache.LAST_UPDATE`); the original is never touched.
- Preview generation (#69): `PreviewCache.createPreview` throttles only the *generation* of a preview — `--preview-threads <n>` / the system property `valbum.previewThreads` / `availableProcessors()` permits of a `Semaphore`, deliberately not a limit derived from free memory (the reasoning is in the Javadoc of `PreviewCache.permits`); serving a preview that is already cached takes no permit. A `ConcurrentHashMap` of in-flight futures keyed by the preview's absolute path makes concurrent requests for the same uncached file wait for the one generation and share its outcome (the same `PreviewException` for every waiter, the entry dropped so a later request may retry); the preview is written to `preview-<name>.tmp` in `.vacache` and moved into place with `ATOMIC_MOVE` (falling back to `REPLACE_EXISTING`), so nothing ever serves a half-written file.
- Static web content: the server serves `META-INF/resources` of the class path (the Flutter web build, icons included, if `valbum_ui/build/web` existed at `package` time) at the context root; `--webroot <dir>` serves a directory from disk with precedence over the class path. Unknown paths without a file extension fall back to `index.html` (client-side deep links).
- Test fixtures live at `image-server/src/test/fixtures/test-album`.
- Java lint/format (Spotless, lightweight — tidies imports/whitespace, preserves tab indentation; **not** bound to a build phase): `mvn spotless:check` / `mvn spotless:apply`.

### Flutter (`valbum_ui/`)

- Use the `flutter` CLI: `flutter pub get`, `flutter analyze`, `flutter test`, `flutter run -d chrome`. The Flutter SDK lives in `~/flutter`, the Android SDK in `~/Android/Sdk` (both on PATH via `~/.bashrc`).
- Server URL: on the web derived from the page origin (`lib/urls.dart`, `deriveDataUrl`); on other platforms the default `http://localhost:9090/valbum/data` until the settings screen (ROADMAP Phase 2). All HTTP goes through `lib/client.dart` (`VAlbumClient`), injected via `VAlbumScope` — tests pass a `MockClient`. Sessions (#51, #52): an app base `<context>/s/<token>/` or `<context>/i/<token>/` is a share link or an invitation (`urls.dart` `sessionUrl`/`SessionUrl`, one mechanism, two kinds); the token is the bearer for one `?type=auth`, whose answer opens the album (`share_session.dart`), the welcome-and-join screen (`invitation.dart`), or — for a token the server knows as neither — the ordinary start. The device's stored server and token are never read in a session and a session token is never stored; joining stores the plain server URL and the device token like a sign-in, then `leaveForUrl` (`platform_*.dart`) replaces the location with `<context>/`. `serverLocationOf` lets the settings' server field accept a pasted invitation URL (and refuses a share link there). The caller's role comes from one `?type=auth` per client (`caller.dart`, `CallerScope`) and hides at a guest's own root what the server refuses by role.

## Gotchas

- **Model classes are generated.** `image-server-shared/src/main/java/.../shared/model/model.proto` is the source of truth; the msgbuf-generator Maven plugin regenerates the model on every build. Edit the `.proto`, never the generated output. This generates **both** the Java model classes **and** the Dart file `valbum_ui/lib/resource.dart` (see the `option DartLib=...` line in `model.proto`) — `resource.dart` is generated, so don't hand-edit or reformat it.
- **Java 21** (`maven.compiler.release` in the root pom). The former 1.8 setting was a GWT constraint and is gone; a JDK 21 is required to build (the Maven enforcer checks it).

## Conventions

- Commit directly to `master` and push after every reviewed, gated change (see the `valbum-workflow` skill). Feature branches and PRs are for external contributors, not for the working session.
