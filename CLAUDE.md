# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VAlbum2 — a self-hosted photo/video album. A Java backend (Jetty) serves albums read from a folder tree as a JSON API; it never modifies or deletes the original photos (all edits are stored in sidecar files; the only file operations on originals are same-filesystem renames — the explicit library migration and the album move of #47, which sets duplicates aside in `.valbum/duplicates/`). The only front end is the Flutter app in **`valbum_ui/`** (web, mobile, desktop). The former GWT web client was removed in ROADMAP Phase 0.

Direction, phases and decisions are recorded in `ROADMAP.md`.

## Two separate toolchains

This repo mixes **Maven** (Java backend, multi-module: `image-server`, `image-server-shared`, `util-servlet`) and **Flutter/Dart** (`valbum_ui/`), with independent dependency management. A full build means running both.

### Maven (backend)

- Build everything: `mvn clean install` (run from repo root)
- Run the demo server: `mvn exec:java@test-server -pl :image-server` → http://localhost:9090/valbum/ (port 9090, non-standard)
- Run the packaged jar: `java -jar image-server/target/image-server-jar-with-dependencies.jar --basepath /path/to/photos [--port 8080] [--contextpath valbum] [--webroot /path/to/flutter/build/web] [--auth off|writes|all] [--pairing-secret <secret>] [--invite admin|members] [--preview-threads <n>] [--migrate-to-user <name>]`
- Authentication (#28): `--auth` defaults to `writes` — anonymous reads are served, anonymous PUT/POST are refused with 401 and an `ErrorInfo` body. A device pairs with `POST <data>/?action=pair` against the pairing secret (printed at start-up, `demo` for the demo server) and then sends `Authorization: Bearer <token>`; `GET <data>/?type=auth` reports the caller's state (mode, device, user, role, space). Users (#45): the pairing request may carry a `userName`; the secret signs in the library owner (admin), whose name is chosen once. Users with their roles, spaces and devices live in `<basepath>/.valbum/users.json` (token hashes only; a pre-#45 `devices.json` is taken over on first start). Every request path resolves against the caller's space folder; the owner's space is the base folder until `--migrate-to-user <name>` moves the library into `<basepath>/<name>/` (explicit, one-time, rename-only, server not started). A migrated library refuses anonymous callers in every mode but `off`. Privacy (#46): `ImagePart.privacy` 0..2 is enforced on the way out — listings omit parts above the caller's clearance (owner of the space: private; anonymous: public; `--auth off`: everything), image/thumbnail/preview endpoints refuse them (401 anonymous, 403 signed in), `?viewAs=public|members` lowers one's own clearance for a request; `PrivacyFilter` + `AuthService.clearance(...)`, cache and sidecars untouched. Moving (#47): `POST <folder>/?action=move` with a `MoveRequest` (target folder, names) answers a `MoveResult` with one outcome per name; `MoveService` renames files/folders, carries the `ImagePart` and its `.hashes.json` entry into the target sidecar, reuses the upload's free-name rule, sets duplicates aside; rights hooks `AuthService.mayEdit/mayContribute` are the #49 seam. Groups and grants (#49): sharing is one mechanism — a grant `{owner, path, subject, rights, created}` in `<basepath>/.valbum/grants.json` says who (`user:<name>`, `group:<name>`, `anonymous`, later `token:<id>`) may do what (`view`, `download`, `contribute`, `edit`, with `edit`⇒`contribute`/`download`/`view` and those ⇒`view`) on which subtree, inherited downwards; named groups live in `.valbum/groups.json`. `AuthService.rights(caller, path)` is the one method — the owner of a space holds everything in it, the admin holds nothing extra (they manage, they do not browse) — and every endpoint asks it (listing/thumbnail → `view`, original → `download`, sidecar PUT/move source/`?action=place` → `edit`, upload/`?action=check`/move target/album creation → `contribute`/`edit` on the parent). `<data>/~<owner>/<path>` is the canonical form reaching another user's space (404 for an unknown user; a top-level name starting with `~` is refused on creation, upload and move). Whose space a path lies in is the *deepest* space folder containing it (`AuthService.spaceOf`), so a grant stops at the boundary of another user's space; every path the server answers is spelled in the coordinates of the request that asked (`Location.spell`, `~<owner>/...` stays `~<owner>/...`). `FolderResource.rights` is derived on every folder read and cleared by `AlbumDate.clearDerived` before any sidecar write. Management: `GET <folder>/?type=grants`, `POST <folder>/?action=grant|revoke`, `GET <data>/?type=groups|users`, `POST <data>/?action=group|ungroup`. Share links (#51): `POST <folder>/?action=share` with a `ShareLink` (label, expires, maxPrivacy, minRating, rights ⊆ view/download/contribute) records `{id, tokenHash, owner, path, …}` in `<basepath>/.valbum/shares.json` plus a grant to `token:<id>` and answers `ShareLinkCreated` (token once, `url` = `<context>/s/<token>/`); `GET <folder>/?type=shares`, `POST ?action=unshare` (id); the grant API refuses `token:` subjects. A bearer that is a share token makes a link caller: its `/` is the shared folder (outside = 404 `SHARE_CONFINED`), reads even in a migrated library, writes only with `contribute`, clearance `min(MEMBERS, maxPrivacy)`, `PrivacyFilter` also drops parts below `minRating`; expired/revoked → 410 on every endpoint (`LINK_EXPIRED`/`LINK_REVOKED`); `AuthInfo.share` (`ShareInfo{label, expires, rights, path}`) is set for link callers only. `ResourceServlet` serves the app under `/s/<segment>/` with a rebased `<base href>`. Links (#50): a shared album appears in the recipient's tree as a link entry in the folder's `.links.json` sidecar (`{name, owner, path}`); `AuthService.resolve` walks paths segment by segment and follows a link to its target, so rights/clearance are checked on the target while answers are spelled in the viewer's path; `FolderInfo.link` (canonical `~owner/path`, derived) marks a link tile built from the target's sidecar; links are materialised on a member's own root listing from the grants naming them, filed by the root's rule, and remembered in `<space>/.valbum/share-registry.json` (`linked|declined`); `MoveService` moves links between sidecars, `POST <folder>/?action=unlink` declines one; `links/{LinkStore,ShareRegistry,LinkService}`. Invitations and guests (#52): `POST <data>/?action=invite` (a member, or the admin alone under `--invite admin`; body `Invitation{role member|guest, expires (empty = 7 days), note}`) records `{id, tokenHash, role, invitedBy, note, expires, used, usedBy, created, revoked}` in `<basepath>/.valbum/invitations.json` (`auth/InvitationStore`) and answers `InvitationCreated` (token once, `url` = `<context>/i/<token>/`); `GET <data>/?type=invitations` (admin: all, member: own), `POST ?action=uninvite` (id). Accepting is pairing: `PairRequest.invitation` instead of `secret` with a free `userName` (`UserStore.checkUserName`; not a user, group or top-level folder; no leading `~`) creates the user with the invitation's role — a member's space folder on the spot (409 `SPACE_REFUSED` in an un-migrated library) — and marks it used; a dead invitation is 410. An invitation bearer is anonymous everywhere but `?type=auth`, which answers `AuthInfo.invitation` (`InvitationInfo{role, invitedBy, note, expires}`). A guest's root is `<basepath>/.valbum/guests/<name>/` (`AuthService.guestRoot`), a space root shaped like a member's (links, share registry) that never holds a photo: creation, upload and move-target there are refused by role (`GUEST_SPACE_REFUSED`), grants on it refused (`GUEST_GRANT_REFUSED`); `POST <data>/?action=promote` (`MemberName`, admin only) renames it to `<basepath>/<name>/` and makes the guest a member. Token lookup: devices, then shares, then invitations. `ResourceServlet` serves the app under `/i/<segment>/` like `/s/<segment>/`. Every JSON answer (listings, `?type=auth`, every `ErrorInfo`) carries `Cache-Control: no-store` and `Vary: Authorization` (`ImageServlet.allowCrossOrigin`): browsers cache a `410` by default, and a withdrawn link's answer would otherwise be replayed for the next token at the same origin. Attribution (#53): `.hashes.json` entries carry `contributor` (the uploader's `Caller.subject()`: `user:<name>`, `token:<id>`, `anonymous`) and `contributorLabel` (copied at upload), written by both upload paths (`HashCache.put(file, hash, attribution)`; a `PRESENT` upload keeps the first contributor; `refresh()` rehashes but keeps attribution; old files read with empty attribution); `ImagePart.contributor`/`contributorLabel` are derived on read (`Contributors.derive` in `ResourceCache`) and cleared before any sidecar write (`AlbumDate.clearDerived`); `MoveService.landFile` carries the attribution; a move out of an album needs `edit` on the source or the caller as contributor of every named image (`MoveService.contributedBy`, `CONTRIBUTION_REFUSED`; a `token:` caller → `SHARE_MOVE_REFUSED`). Uploads invalidate the resource cache. Management screens (#55, server half): every device carries a short random `id` assigned at pairing (a pre-#55 `users.json` gets ids on the first load and is written back once; the field is skipped by the build before). `GET <data>/?type=devices` answers the caller's **own** devices (`DeviceList{DeviceEntry{id, name, created, current}}`, no token hashes; share link → 403 `DEVICES_REFUSED`, anonymous/invitation → 401), `POST <data>/?action=unpair` with a `DeviceEntry` id removes one of one's own (another user's or an unknown id → 404 `DEVICE_UNKNOWN`; unpairing the asking device is allowed and is "sign out here"); the admin manages users, not other people's devices. `UserEntry` also carries `space`, `created` and `devices` (count). `POST <data>/?action=regroup` with a `GroupRename{name, newName}` renames a group (owner or admin) and rewrites every `group:<name>` grant in the same step — groups.json first, grants.json second, so a crash between the two writes only unshares (fail-closed) and renaming back repairs it — answering the `GroupList`. A group is never named like a user (creation and rename both 409 `groupNameIsUser`), as a user is never named like a group. Adding a device of one's own (#65): a device *code*, never a link and deliberately nothing that reads like an invitation — `POST <data>/?action=device-code` by a signed-in device (share link → 403 `DEVICE_CODE_REFUSED`, anonymous/invitation → 401, `--auth off` → 403 `PAIRING_DISABLED`) answers `DeviceCodeCreated{code, expires}` with eight characters of `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` shown as `XXXX-XXXX`, living 10 minutes and working once; `{id, codeHash, user, issuedBy, created, expires, used, usedBy}` in `<basepath>/.valbum/device-codes.json` (`auth/DeviceCodeStore`, injectable `Clock`, dead entries dropped 24 h after they died), the plain code never stored and normalised (upper case, no dashes or spaces) before hashing. It is never a bearer and never a URL — no `/d/<segment>/`, no token lookup, nothing in `?type=auth` — it exists only as `PairRequest.deviceCode`: `pair` reads a non-empty `invitation` first, then a non-empty `deviceCode` (unknown → 401, used/expired/user gone → 410, a `userName` naming somebody else → 401), else the secret, and a code pairs an ordinary further device of the *same* user, visible in `?type=devices` at once. A code is good only while the device that issued it (`issuedBy`) is still one of its user's devices: `pair` refuses otherwise with 410 `DEVICE_CODE_ISSUER_GONE`, and `unpair` ("sign out here" included) marks every unused code of the device `revoked` (`DeviceCodeStore.revokeIssuedBy`), so throwing a stranger's device out also takes back what it handed out; the device a code created is an ordinary device, not a child of the issuer. In the app the devices section carries "Add a device…" (`settings.devices.add`) opening `settings.deviceCode.dialog` (code, countdown, the joined line; it re-reads the device list every 3 s through an injectable ticker) and the sign-in section a device code field (`settings.deviceCode`) beside the pairing secret, refusing both at once before any request. Cameras (#78): `ImagePart.camera` is a short label built by `ImageData.cameraLabel(make, model)` from the EXIF `Make`/`Model` of a photo (both trimmed, blanks collapsed, joined with one blank, the make left out when the model already begins with it as a whole word ignoring case — `Canon`+`Canon EOS 5D` → `Canon EOS 5D`, `NIKON CORPORATION`+`NIKON D750` → `NIKON CORPORATION NIKON D750`); a video takes it from `QuickTimeMetadataDirectory` where the container has it, which the phones' MP4s do not, so their videos carry the empty label. Read at analysis time and **stored** in the sidecar like `date` (not cleared by `AlbumDate.clearDerived`), so a part a sidecar already lists keeps no camera until it is analysed afresh. Video dates (#72): `ImageData.analyze` dates a video by the `mvhd` creation time of its container (`Mp4Directory.TAG_CREATION_TIME`, `QuickTimeDirectory` for QuickTime), taken as metadata-extractor hands it out exactly as the EXIF date is; a container time before `ImageData.EARLIEST_RECORDING` (1990-01-01 UTC, which the unset QuickTime epoch 1904 falls below) is no recording time and the file's modification time stands. Only albums analysed afresh get the new order — `AlbumUtil.insertSorted` inserts new parts among the stored ones and never resorts them, so a written sidecar keeps the author's order and the parts' stored dates. Dates and placement (#48): `AlbumInfo.date` is the explicit date (stored), `AlbumInfo.effectiveDate`/`FolderInfo.effectiveDate` are derived on read by `AlbumDate` (explicit → folder-name date → earliest image date; listing tiles never open images) and cleared to 0 before any sidecar write; listings sort newest first, undated by name; `ListingInfo.placement` (`NONE|BY_YEAR|BY_YEAR_MONTH`, stored in the folder's sidecar) is applied by `PlacementRule` when an album is created (the creating PUT answers a `CreateResult` with the final space-relative path) or moved into the folder, and by `POST <folder>/?action=place` (apply once, a `MoveResult`).
- Video renditions (#74): beside the poster frame, `VideoRenditions` (one per servlet, shut down in `ImageServlet.destroy()`) makes two sidecars per video in the album's `.vacache` — `video-<name>.mp4` (faststart, H.264 720 px short side, ≤30 fps, AAC) and `teaser-<name>.mp4` (~3 s from ~10 % in, silent, 240 px, faststart) — with the FFmpeg *program* of the bundled `org.bytedeco:ffmpeg` (`Loader.load(org.bytedeco.ffmpeg.ffmpeg.class)`), run as a child process with an argument list (never a command string), `-threads` at half the processors, one transcode at a time on a dedicated single-thread executor independent of the #69 preview permits. The encoder is chosen once by asking the program (`-encoders`): `libx264` if present, else `libopenh264` (what the LGPL build ships), else nothing is transcoded. `?type=video` / `?type=teaser` on an image path need `view` like the thumbnail and answer `video/mp4` over the existing range path; a rendition not yet made is never awaited — `202` + `ErrorInfo` `RENDITION_PENDING` + `Retry-After: 10` and the transcode is queued (deduplicated per rendition); a failed transcode is remembered for the process lifetime and answered `500` + `RENDITION_FAILED` with the FFmpeg tail in the log. Written to `.tmp` and moved atomically, invalidated like previews (`PreviewCache.LAST_UPDATE`); the original is never touched.
- Preview generation (#69): `PreviewCache.createPreview` throttles only the *generation* of a preview — `--preview-threads <n>` / the system property `valbum.previewThreads` / `availableProcessors()` permits of a `Semaphore`, deliberately not a limit derived from free memory (the reasoning is in the Javadoc of `PreviewCache.permits`); serving a preview that is already cached takes no permit. A `ConcurrentHashMap` of in-flight futures keyed by the preview's absolute path makes concurrent requests for the same uncached file wait for the one generation and share its outcome (the same `PreviewException` for every waiter, the entry dropped so a later request may retry); the preview is written to `preview-<name>.tmp` in `.vacache` and moved into place with `ATOMIC_MOVE` (falling back to `REPLACE_EXISTING`), so nothing ever serves a half-written file.
- Static web content: the server serves `META-INF/resources` of the class path (the Flutter web build, icons included, if `valbum_ui/build/web` existed at `package` time) at the context root; `--webroot <dir>` serves a directory from disk with precedence over the class path. Unknown paths without a file extension fall back to `index.html` (client-side deep links).
- Test fixtures live at `image-server/src/test/fixtures/test-album`.
- Java lint/format (Spotless, lightweight — tidies imports/whitespace, preserves tab indentation; **not** bound to a build phase): `mvn spotless:check` / `mvn spotless:apply`.

### Flutter (`valbum_ui/`)

- Use the `flutter` CLI: `flutter pub get`, `flutter analyze`, `flutter test`, `flutter run -d chrome`. The Flutter SDK lives in `~/flutter`, the Android SDK in `~/Android/Sdk` (both on PATH via `~/.bashrc`).
- Server URL: on the web derived from the page origin (`lib/urls.dart`, `deriveDataUrl`); on other platforms the default `http://localhost:9090/valbum/data` until the settings screen (ROADMAP Phase 2). All HTTP goes through `lib/client.dart` (`VAlbumClient`), injected via `VAlbumScope` — tests pass a `MockClient`. Sessions (#51, #52): an app base `<context>/s/<token>/` or `<context>/i/<token>/` is a share link or an invitation (`urls.dart` `sessionUrl`/`SessionUrl`, one mechanism, two kinds); the token is the bearer for one `?type=auth`, whose answer opens the album (`share_session.dart`), the welcome-and-join screen (`invitation.dart`), or — for a token the server knows as neither — the ordinary start. The device's stored server and token are never read in a session and a session token is never stored; joining stores the plain server URL and the device token like a sign-in, then `leaveForUrl` (`platform_*.dart`) replaces the location with `<context>/`. `serverLocationOf` lets the settings' server field accept a pasted invitation URL (and refuses a share link there). The caller's role comes from one `?type=auth` per client (`caller.dart`, `CallerScope`) and hides at a guest's own root what the server refuses by role.

## Gotchas

- **Model classes are generated.** `image-server-shared/src/main/java/.../shared/model/model.proto` is the source of truth; the msgbuf-generator Maven plugin regenerates the model on every build. Edit the `.proto`, never the generated output. This generates **both** the Java model classes **and** the Dart file `valbum_ui/lib/resource.dart` (see the `option DartLib=...` line in `model.proto`) — `resource.dart` is generated, so don't hand-edit or reformat it.
- **Java 21** (`maven.compiler.release` in the root pom). The former 1.8 setting was a GWT constraint and is gone; a JDK 21 is required to build (the Maven enforcer checks it).

## Conventions
