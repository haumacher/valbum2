# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VAlbum2 — a self-hosted photo/video album. A Java backend (Jetty) serves albums read from a folder tree as a JSON API; it never modifies or deletes the original photos (all edits are stored in sidecar files; the only file operations on originals are same-filesystem renames — the explicit library migration and the album move of #47, which sets duplicates aside in `.valbum/duplicates/`). The only front end is the Flutter app in **`valbum_ui/`** (web, mobile, desktop). The former GWT web client was removed in ROADMAP Phase 0.

Direction, phases and decisions are recorded in `ROADMAP.md`.

## Two separate toolchains

This repo mixes **Maven** (Java backend, multi-module: `image-server`, `image-server-shared`, `util-servlet`) and **Flutter/Dart** (`valbum_ui/`), with independent dependency management. A full build means running both.

### Maven (backend)

- Build everything: `mvn clean install` (run from repo root)
- Run the demo server: `mvn exec:java@test-server -pl :image-server` → http://localhost:9090/valbum/ (port 9090, non-standard)
- Run the packaged jar: `java -jar image-server/target/image-server-jar-with-dependencies.jar --basepath /path/to/photos [--port 8080] [--contextpath valbum] [--webroot /path/to/flutter/build/web] [--auth off|writes|all] [--pairing-secret <secret>] [--invite admin|members] [--migrate-to-user <name>]`
- Authentication (#28): `--auth` defaults to `writes` — anonymous reads are served, anonymous PUT/POST are refused with 401 and an `ErrorInfo` body. A device pairs with `POST <data>/?action=pair` against the pairing secret (printed at start-up, `demo` for the demo server) and then sends `Authorization: Bearer <token>`; `GET <data>/?type=auth` reports the caller's state (mode, device, user, role, space). Users (#45): the pairing request may carry a `userName`; the secret signs in the library owner (admin), whose name is chosen once. Users with their roles, spaces and devices live in `<basepath>/.valbum/users.json` (token hashes only; a pre-#45 `devices.json` is taken over on first start). Every request path resolves against the caller's space folder; the owner's space is the base folder until `--migrate-to-user <name>` moves the library into `<basepath>/<name>/` (explicit, one-time, rename-only, server not started). A migrated library refuses anonymous callers in every mode but `off`. Privacy (#46): `ImagePart.privacy` 0..2 is enforced on the way out — listings omit parts above the caller's clearance (owner of the space: private; anonymous: public; `--auth off`: everything), image/thumbnail/preview endpoints refuse them (401 anonymous, 403 signed in), `?viewAs=public|members` lowers one's own clearance for a request; `PrivacyFilter` + `AuthService.clearance(...)`, cache and sidecars untouched. Moving (#47): `POST <folder>/?action=move` with a `MoveRequest` (target folder, names) answers a `MoveResult` with one outcome per name; `MoveService` renames files/folders, carries the `ImagePart` and its `.hashes.json` entry into the target sidecar, reuses the upload's free-name rule, sets duplicates aside; rights hooks `AuthService.mayEdit/mayContribute` are the #49 seam. Groups and grants (#49): sharing is one mechanism — a grant `{owner, path, subject, rights, created}` in `<basepath>/.valbum/grants.json` says who (`user:<name>`, `group:<name>`, `anonymous`, later `token:<id>`) may do what (`view`, `download`, `contribute`, `edit`, with `edit`⇒`contribute`/`download`/`view` and those ⇒`view`) on which subtree, inherited downwards; named groups live in `.valbum/groups.json`. `AuthService.rights(caller, path)` is the one method — the owner of a space holds everything in it, the admin holds nothing extra (they manage, they do not browse) — and every endpoint asks it (listing/thumbnail → `view`, original → `download`, sidecar PUT/move source/`?action=place` → `edit`, upload/`?action=check`/move target/album creation → `contribute`/`edit` on the parent). `<data>/~<owner>/<path>` is the canonical form reaching another user's space (404 for an unknown user; a top-level name starting with `~` is refused on creation, upload and move). Whose space a path lies in is the *deepest* space folder containing it (`AuthService.spaceOf`), so a grant stops at the boundary of another user's space; every path the server answers is spelled in the coordinates of the request that asked (`Location.spell`, `~<owner>/...` stays `~<owner>/...`). `FolderResource.rights` is derived on every folder read and cleared by `AlbumDate.clearDerived` before any sidecar write. Management: `GET <folder>/?type=grants`, `POST <folder>/?action=grant|revoke`, `GET <data>/?type=groups|users`, `POST <data>/?action=group|ungroup`. Share links (#51): `POST <folder>/?action=share` with a `ShareLink` (label, expires, maxPrivacy, minRating, rights ⊆ view/download/contribute) records `{id, tokenHash, owner, path, …}` in `<basepath>/.valbum/shares.json` plus a grant to `token:<id>` and answers `ShareLinkCreated` (token once, `url` = `<context>/s/<token>/`); `GET <folder>/?type=shares`, `POST ?action=unshare` (id); the grant API refuses `token:` subjects. A bearer that is a share token makes a link caller: its `/` is the shared folder (outside = 404 `SHARE_CONFINED`), reads even in a migrated library, writes only with `contribute`, clearance `min(MEMBERS, maxPrivacy)`, `PrivacyFilter` also drops parts below `minRating`; expired/revoked → 410 on every endpoint (`LINK_EXPIRED`/`LINK_REVOKED`); `AuthInfo.share` (`ShareInfo{label, expires, rights, path}`) is set for link callers only. `ResourceServlet` serves the app under `/s/<segment>/` with a rebased `<base href>`. Links (#50): a shared album appears in the recipient's tree as a link entry in the folder's `.links.json` sidecar (`{name, owner, path}`); `AuthService.resolve` walks paths segment by segment and follows a link to its target, so rights/clearance are checked on the target while answers are spelled in the viewer's path; `FolderInfo.link` (canonical `~owner/path`, derived) marks a link tile built from the target's sidecar; links are materialised on a member's own root listing from the grants naming them, filed by the root's rule, and remembered in `<space>/.valbum/share-registry.json` (`linked|declined`); `MoveService` moves links between sidecars, `POST <folder>/?action=unlink` declines one; `links/{LinkStore,ShareRegistry,LinkService}`. Invitations and guests (#52): `POST <data>/?action=invite` (a member, or the admin alone under `--invite admin`; body `Invitation{role member|guest, expires (empty = 7 days), note}`) records `{id, tokenHash, role, invitedBy, note, expires, used, usedBy, created, revoked}` in `<basepath>/.valbum/invitations.json` (`auth/InvitationStore`) and answers `InvitationCreated` (token once, `url` = `<context>/i/<token>/`); `GET <data>/?type=invitations` (admin: all, member: own), `POST ?action=uninvite` (id). Accepting is pairing: `PairRequest.invitation` instead of `secret` with a free `userName` (`UserStore.checkUserName`; not a user, group or top-level folder; no leading `~`) creates the user with the invitation's role — a member's space folder on the spot (409 `SPACE_REFUSED` in an un-migrated library) — and marks it used; a dead invitation is 410. An invitation bearer is anonymous everywhere but `?type=auth`, which answers `AuthInfo.invitation` (`InvitationInfo{role, invitedBy, note, expires}`). A guest's root is `<basepath>/.valbum/guests/<name>/` (`AuthService.guestRoot`), a space root shaped like a member's (links, share registry) that never holds a photo: creation, upload and move-target there are refused by role (`GUEST_SPACE_REFUSED`), grants on it refused (`GUEST_GRANT_REFUSED`); `POST <data>/?action=promote` (`MemberName`, admin only) renames it to `<basepath>/<name>/` and makes the guest a member. Token lookup: devices, then shares, then invitations. `ResourceServlet` serves the app under `/i/<segment>/` like `/s/<segment>/`. Every JSON answer (listings, `?type=auth`, every `ErrorInfo`) carries `Cache-Control: no-store` and `Vary: Authorization` (`ImageServlet.allowCrossOrigin`): browsers cache a `410` by default, and a withdrawn link's answer would otherwise be replayed for the next token at the same origin. Dates and placement (#48): `AlbumInfo.date` is the explicit date (stored), `AlbumInfo.effectiveDate`/`FolderInfo.effectiveDate` are derived on read by `AlbumDate` (explicit → folder-name date → earliest image date; listing tiles never open images) and cleared to 0 before any sidecar write; listings sort newest first, undated by name; `ListingInfo.placement` (`NONE|BY_YEAR|BY_YEAR_MONTH`, stored in the folder's sidecar) is applied by `PlacementRule` when an album is created (the creating PUT answers a `CreateResult` with the final space-relative path) or moved into the folder, and by `POST <folder>/?action=place` (apply once, a `MoveResult`).
- Static web content: the server serves `META-INF/resources` of the class path (the Flutter web build, icons included, if `valbum_ui/build/web` existed at `package` time) at the context root; `--webroot <dir>` serves a directory from disk with precedence over the class path. Unknown paths without a file extension fall back to `index.html` (client-side deep links).
- Test fixtures live at `image-server/src/test/fixtures/test-album`.
- Java lint/format (Spotless, lightweight — tidies imports/whitespace, preserves tab indentation; **not** bound to a build phase): `mvn spotless:check` / `mvn spotless:apply`.

### Flutter (`valbum_ui/`)

- Use the `flutter` CLI: `flutter pub get`, `flutter analyze`, `flutter test`, `flutter run -d chrome`. The Flutter SDK lives in `~/flutter`, the Android SDK in `~/Android/Sdk` (both on PATH via `~/.bashrc`).
- Server URL: on the web derived from the page origin (`lib/urls.dart`, `deriveDataUrl`); on other platforms the default `http://localhost:9090/valbum/data` until the settings screen (ROADMAP Phase 2). All HTTP goes through `lib/client.dart` (`VAlbumClient`), injected via `VAlbumScope` — tests pass a `MockClient`. Sessions (#51, #52): an app base `<context>/s/<token>/` or `<context>/i/<token>/` is a share link or an invitation (`urls.dart` `sessionUrl`/`SessionUrl`, one mechanism, two kinds); the token is the bearer for one `?type=auth`, whose answer opens the album (`share_session.dart`), the welcome-and-join screen (`invitation.dart`), or — for a token the server knows as neither — the ordinary start. The device's stored server and token are never read in a session and a session token is never stored; joining stores the plain server URL and the device token like a sign-in, then `leaveForUrl` (`platform_*.dart`) replaces the location with `<context>/`. `serverLocationOf` lets the settings' server field accept a pasted invitation URL (and refuses a share link there). The caller's role comes from one `?type=auth` per client (`caller.dart`, `CallerScope`) and hides at a guest's own root what the server refuses by role.

## Gotchas

- **Model classes are generated.** `image-server-shared/src/main/java/.../shared/model/model.proto` is the source of truth; the msgbuf-generator Maven plugin regenerates the model on every build. Edit the `.proto`, never the generated output. This generates **both** the Java model classes **and** the Dart file `valbum_ui/lib/resource.dart` (see the `option DartLib=...` line in `model.proto`) — `resource.dart` is generated, so don't hand-edit or reformat it.
- **Java 21** (`maven.compiler.release` in the root pom). The former 1.8 setting was a GWT constraint and is gone; a JDK 21 is required to build (the Maven enforcer checks it).

## Conventions

- Commit directly to `master` and push after every reviewed, gated change (see the `valbum-workflow` skill). Feature branches and PRs are for external contributors, not for the working session.
