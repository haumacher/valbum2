# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

VAlbum2 — a self-hosted photo/video album. A Java backend (Jetty) serves albums read from a folder tree as a JSON API; it never modifies or deletes the original photos (all edits are stored in sidecar files; the only file operations on originals are same-filesystem renames — the explicit library migration, the album move of #47, which sets duplicates aside in `<space>/.valbum/duplicates/`, and the delete of #109, which renames an album holding photographs into `<space>/.valbum/trash/`). The only front end is the Flutter app in **`valbum_ui/`** (web, mobile, desktop). The former GWT web client was removed in ROADMAP Phase 0.

Direction, phases and decisions are recorded in `ROADMAP.md`.

## Two separate toolchains

This repo mixes **Maven** (Java backend, multi-module: `image-server`, `image-server-shared`, `util-servlet`) and **Flutter/Dart** (`valbum_ui/`), with independent dependency management. A full build means running both.

### Maven (backend)

- Build everything: `mvn clean install` (run from repo root)
- Run the demo server: `mvn exec:java@test-server -pl :image-server` → http://localhost:9090/valbum/ (port 9090, non-standard)
- Run the packaged jar: `java -jar image-server/target/image-server-jar-with-dependencies.jar --basepath /path/to/photos [--port 8080] [--contextpath valbum] [--webroot /path/to/flutter/build/web] [--auth off|writes|all] [--admin-code <code>] [--invite admin|members] [--preview-threads <n>] [--migrate-to-user <name>]`
- Authentication and permissions (#28, #45, #82, #83): `--auth` (`off|writes|all`) says what an anonymous caller may do; a device pairs with `POST <data>/?action=pair` carrying a **code** (#89: one single-use secret, ten minutes, one device, one target user — the seat code the server prints, a code of one's own device, a recovery code from an administrator) and then sends `Authorization: Bearer <token>`. **A space is the unit of everything**: one server hosts one space (the base folder, today's addresses) or several (#82). A user belongs to exactly one space, lives in that space's `<space>/.valbum/users.json` with their devices, and holds **one permission for the whole space**: `{role: admin|edit|contribute|view, clearance: public|nonPrivate|all, mayShare: bool}` (#83). `AuthService.rights(caller, path)` answers from the role alone and the same for every path — admin/edit → view+download+contribute+edit, contribute → view+download+contribute, view → view+download; a share link answers what the link itself was created with; an anonymous caller answers view+download where the space is open (`--auth writes`, or `space.json` `anonymous: public`) and nothing otherwise. `AuthService.clearance(...)` answers the stored clearance (admin: everything; anonymous: public), `?viewAs=public|members` lowers one's own for a request, and `PrivacyFilter` drops what is above it on the way out (`ImagePart.privacy` 0..2, cache and sidecars untouched). Every endpoint asks those two: listing/thumbnail → `view`, original → `download`, sidecar PUT / move source / `?action=place` → `edit`, upload / `?action=check` / move target / album creation → `contribute`. `Roles.of` reads the older names of a library written before #83 (`member` → edit/all/share, `guest` → view/nonPrivate/no-share) without rewriting the file, and the protocol answers the new names. Management (admin only): `GET <data>/?type=users` (role, clearance, mayShare, devices), `POST <data>/?action=invite|uninvite` (the invitation carries role/clearance/mayShare, capped at the inviter's), `?action=set-permission` (`UserPermission{name, role, clearance, mayShare}`; the last admin is never demoted, 409 `LAST_ADMIN`), `?action=remove-user` (`MemberName`; their devices go, their photos and their attribution stay). **Retired by #83, answering 410 with an `ErrorInfo` naming the replacement for one release**: `?type=grants|groups|links`, `?action=grant|revoke|group|ungroup|regroup|unlink|promote` — grants, groups, materialised links, guest roots and the `~<owner>/` path form are gone, with their stores (`GrantStore`, `GroupStore`, `Subjects`, `links/*`). Moving (#47): `POST <folder>/?action=move` with a `MoveRequest` answers a `MoveResult` per name; `MoveService` renames only, carries the `ImagePart` and its `.hashes.json` entry along, sets duplicates aside; a move out of an album needs `edit` or the caller as contributor of every named image (`CONTRIBUTION_REFUSED`); the kind of the target decides (#113) — an image whose target is a folder of folders is refused `notAnAlbum(name)` and an album or folder whose target is an album `notAFolder(name)`, both before anything is renamed. Deleting (#109) is that move with the trash as its target: `POST <parent>/?action=delete` with the same `MoveRequest` (`target` empty and ignored) answers the same `MoveResult`, needs **`edit`** on the parent (a share link 403 `SHARE_DELETE_REFUSED`, the contributor exception of #53 does not reach a whole album), and acts on **albums and folders only** (an image is taken out by moving it, `DeleteService.notAnEntry`). `DeleteService` decides per name: a folder that holds **no picture anywhere below it** — `ResourceCache.isImage`, a photo rated −2 counting as a picture, a file in `.vacache` counting unless `CacheRefresh.isGenerated` names it — is **removed physically**, and then only what the server itself wrote (`index.json`, its `index.json.<ts>` backups, `.hashes.json`, everything inside `.vacache`) plus the emptied directories; one foreign file anywhere below refuses the removal and the folder goes to the trash instead, files and all (`DeleteService.removable` computes the whole list before anything is touched, pinned by `TestImageServletDelete.testNothingButWhatTheServerWroteIsEverDeleted`). Everything else is **one rename** into `<space>/.valbum/trash/<name>`, sidecars and hashes riding along, previews abandoned; a name the trash already holds gets the prefix `<yyyyMMdd-HHmmss>-<name>` with `-2`, `-3`… behind the whole name (`ImageServlet.freeName` numbers before a file extension and a folder has none). The outcome names which happened — `newName` the name in the trash or `""` for a removal, `message` `REMOVED` or `trashed(name)`. Emptying the trash is the owner's act, never the server's, and **`AuthService.walk` now refuses any path segment starting with `.`** (404 `PATH_ESCAPED`), so no address reaches into `.valbum` — the trash, the duplicates and the user store alike. The **duplicates folder moved per space** in the same change: `MoveService.setAside` writes below `PathInfo.getBasePath()`, the caller's space root, which in single mode *is* the base folder (unchanged paths); what an older multi-space server left below the server base stays there and is named once at start-up (`DeleteService.legacyDuplicates`, printed by `Main.start`). In the app the delete is one shared flow (`move_view.dart` `deleteWithConfirmation`, `client.dart` `delete(...)`): "Delete…" in the listing tile's long-press menu (key `delete-entry`, offered exactly where "Move to…" is) and "Delete album…" in the album menu (key `delete-album`, offered where "Move album to…" is), both refused offline, never in a share session, confirming with `deleteExplanation` — "An album without any image is removed; one with images is moved to the trash folder of the space (nothing is deleted from disk)." — showing the server's own outcome message afterwards and, for the album one is standing in, ascending to the parent as `moveAlbum` does. **The hashes of a space are indexed** (#118): `HashIndex` (`<space>/.valbum/hash-index.json`, `{version, folders: {<path>: {stamp: <mtime of its .hashes.json>, hashes: {<sha256>: <file name>}}}}`) is a lookup of hash → path relative to the space root, **derived** from the per-folder `.hashes.json` sidecars, which stay the stored truth — no database, one map. One index and one low-priority single-thread executor per space, started by `Main.createServer` (`ImageServlet.startIndexing()`, never by a test) and shut down in `destroy()`: the first pass reads the tree, skips every folder whose sidecar stamp is unchanged, and **hashes every folder whose sidecar does not name all its images** (`HashCache.refresh()` + `flush()`, so the sidecar is written and a restart finds it done), resumable, the index file written atomically at most every `WRITE_INTERVAL_MILLIS` (2 s) and always at the end, never on the request path. It is kept current by the one writer of a sidecar — `HashCache.flush()` calls `HashIndex.sidecarWritten(folder)`, which covers the upload, the move and the lazy fill of a check — plus `treeChanged(folder)` after a move or a delete (a folder rename announces nothing), and `pathOf` checks that the file it found is still there, so a stale entry is forgotten rather than answered. `?action=check` therefore answers **space-wide**: the target folder first (a bare name, as before), then the index (`PresentFile.name` becomes a path — `2020/Trip/IMG_1.jpg` — which the app only shows), plus `UploadCheckResult.indexed` (`IndexProgress{done, total}` in folders, `done == total` only when complete, `total = done + 1` while nothing is known); a share-link caller is confined to its folder and told nothing of the index. The sweep is `POST <album>/?action=find-duplicates` (needs `edit`, not admin; a share link and anybody else 403 `DUPLICATES_REFUSED`): `MoveService.setAsideDuplicates` hashes the album and renames every photo whose hash the index finds in **another** folder of the space into `<space>/.valbum/duplicates/` by the #47 mechanism, takes the part out of the sidecar and answers a `MoveResult` naming where the copy that stays is (two copies inside the one album are not duplicates of the space and stay). Share links (#51, #84): `POST <folder>/?action=share` with a `ShareLink` (label, expires, maxPrivacy, minRating, rights) needs the **share flag** (`AuthService.mayShareLinks`, else 403 `SHARING_REFUSED`); `edit` in the rights is 400 `SHARE_EDIT_REFUSED` and a `maxPrivacy` above the creator's own clearance is 400 `shareAboveClearance(...)` — **refused, never quietly trimmed**, so nobody hands out a link they believe shows less than it does. What the link may do and show is written on it (`{id, tokenHash, owner, path, rights, maxPrivacy, minRating, createdBy, created, revoked}` in `<space>/.valbum/shares.json`) and **frozen there**: a later change to its maker's permission neither widens nor narrows it. **The link is the permission — there is no grant beside it.** The answer is `ShareLinkCreated` (token once, `url` = `<context>[/<space>]/s/<token>/`); **a link posted in a messenger shows a card** (#104, `SharePreview`, installed on `ResourceServlet` as the `PageDecorator` and the `SessionResource` beside #88's `SessionGuard`): the page load of a share base only — never an invitation's, never a dead link's — carries `<title>`, `og:title` (the shared album's title, never the link's label), `og:description` (its subtitle, failing that its date), `og:url`, `og:image` and `twitter:card`, HTML-escaped and nothing stored, and the one picture they name is `<context>[/<space>]/s/<token>/cover.jpg` — the `PreviewCache` rendition of the album's index picture (of the first child that has one, for a shared folder), answered **anonymously**, the token in the path being the authority for that one resource and nothing else, with the link's own `min(MEMBERS, maxPrivacy)` and `minRating` through `PrivacyFilter` (an index picture the link may not show falls back to the first image it may, none at all → 404 and no `og:image`), expired/revoked/unknown → 410 with an `ErrorInfo`, `Cache-Control: no-store` and `Vary: Authorization` like every session answer. A share bearer's `/` is the shared folder (outside → 404 `SHARE_CONFINED`), it reads even where the space refuses anonymous callers, contributes only with `contribute` and is attributed `token:<id>`, clearance `min(MEMBERS, maxPrivacy)` (a link never shows a private image, whoever made it), parts below `minRating` dropped, expired/revoked → 410 on **every** endpoint including thumbnails and renditions, `AuthInfo.share` set for link callers only; a token of another space is simply unknown there. Management: `GET <folder>/?type=shares` and `POST ?action=unshare` show and withdraw **one's own** links, an administrator's every link of the space (`ImageServlet.mine`; a link of somebody else's is answered `SHARE_UNKNOWN`, never "whose"); `?action=remove-user` withdraws every link the removed user handed out and says how many in `UserList.revokedLinks`. Invitations (#52, #89): **an invitation is a pending user carrying a code — there is no invitation store any more.** `POST <data>/?action=invite` (body `Invitation{role, clearance, mayShare, note, expires, recipient}`) creates a **pending user** in `<space>/.valbum/users.json` — `name: ""`, no devices, the invitation's permission (capped at the inviter's), plus `invitation` (the code's id), `invitedBy`, `note` and the optional **recipient memento** — and **one code** in `<space>/.valbum/device-codes.json` with `kind: "invitation"`, 32 random bytes base64url, the invitation's expiry (days), exempt from `DEVICE_CODE_ISSUER_GONE` like the backup code; the answer is `InvitationCreated` with the URL `<context>[/<space>]/i/<token>/`. `DeviceCodeStore.lookup` matches an invitation record against the hash of the token **as it stands** and every other record against the normalised typed form, so the two spellings live in one store and a token hashed by the old `InvitationStore` still resolves. Redeeming is the **ordinary pairing**: `PairRequest{deviceCode, userName, deviceName}` → `addDevice` → the pending user is nameless → `NAME_REQUIRED` unless a free `userName` is given → named, first device added, code used (`PairRequest.invitation` is read as an alias of `deviceCode` for one release). `?type=invitations` is **derived** (`AuthService.invitations()` joins pending/invited users with their codes); `?action=uninvite {id}` revokes the code and **removes the pending user if nobody joined** (a named user stays); `?action=remove-user` also withdraws the unaccepted invitations that user sent; an expired invitation's pending user is swept at start-up and before every listing (`AuthService.pruneInvitations`); a pending user never counts for `LAST_ADMIN` and is never named by #86's start-up naming. `?type=users` lists pending users with `UserEntry{pending, recipient, invitedBy, invitation}` (the app shows "Invited for … (pending)" with *Withdraw*); the memento stays beside the name once somebody joined and is **never shown to the invitee**. Dead invitation codes are kept `KEEP_DEAD_INVITATION_DAYS` (30) instead of 24 hours, so #88's reasons survive a month. An `invitations.json` written before this build is carried over once at start-up (`AuthService.adoptInvitations`): every **live** invitation becomes a pending user + a code with the **same token hash**, the dead ones are dropped and the file is moved to `.valbum/retired/<timestamp>/`. An invitation bearer is anonymous everywhere but `?type=auth`, which answers `AuthInfo.invitation` (`InvitationInfo{role, invitedBy, note, expires, recipient}`); only a `kind: "invitation"` code is ever a bearer — a typed device code opens nothing; a **page load** of a dead invitation address (used, expired, withdrawn, unknown to that space) is answered `302` to the space's app base with `?invitation=used|expired|withdrawn|unknown` (#88, `InvitationRedirect` wired into `ResourceServlet.setSessionGuard`; assets and `/s/<token>/` untouched, the record never written). Device codes (#65, #89): `POST <data>/?action=device-code` answers `DeviceCodeCreated{code, expires}` (eight characters of `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, ten minutes, once) stored hashed in `<space>/.valbum/device-codes.json`; it is never a bearer and never a URL, only `PairRequest.deviceCode`, and it dies with the device that issued it (`DEVICE_CODE_ISSUER_GONE`, checked against every device of the space since #89, because an administrator's device may issue for somebody else). The body is an optional `DeviceCodeRequest{userName}`: empty means "for myself" as before, a name is the **recovery code** an administrator makes for an existing user who lost every device (a non-admin naming somebody else → 403 `RECOVERY_REFUSED`, an unknown user → 404 `unknownUser`, an unreadable body → 400 `DEVICE_CODE_UNREADABLE`). Backup code (#92): `POST <data>/?action=backup-code` answers a `DeviceCodeCreated` for the caller themselves — the same record in the same store, told apart by a `kind: "backup"` field (absent/empty = an ordinary code, so an old `device-codes.json` reads unchanged), **16** characters of the same alphabet (80 bits, shown `XXXX-XXXX-XXXX-XXXX`; `DeviceCodeStore.format` groups by four), **`expires` empty = never** (`isExpired` reads an empty expiry as "never" only for a backup code; on any other record it still reads as expired), exempt from `DEVICE_CODE_ISSUER_GONE` and from `revokeIssuedBy` (it is made on the very device one is about to sign out of), single use, **one per user** (creating withdraws the earlier one, which is then refused `BACKUP_CODE_REVOKED`), redeemed through the ordinary pairing in the one code field (the store looks up by hash; the length says nothing). `POST ?action=revoke-backup-code` withdraws it (404 `NO_BACKUP_CODE` where there is none) and answers the device list; a share link is refused 403 `BACKUP_CODE_REFUSED`, an anonymous caller 401. `DeviceList.backupCodeCreated` says whether there is one and since when — never the code. Pruning after `KEEP_DEAD_HOURS` never touches a live backup code. Devices: `GET <data>/?type=devices` answers one's **own** devices, `POST ?action=unpair` removes one of one's own (and revokes the codes it handed out, the backup code excepted). Token lookup: devices, then shares, then invitation codes. `GET <data>/?type=auth` reports mode, device, user, **role, clearance, mayShare**, space, and the share or invitation a token opened. Every JSON answer carries `Cache-Control: no-store` and `Vary: Authorization` (`ImageServlet.allowCrossOrigin`). Attribution (#53): `.hashes.json` entries carry `contributor` (`user:<name>`, `token:<id>`, `anonymous`) and `contributorLabel`, derived onto `ImagePart.contributor`/`contributorLabel` on read and cleared before any sidecar write. Cameras (#78): `ImagePart.camera` is `ImageData.cameraLabel(make, model)` from the EXIF `Make`/`Model` (both trimmed, blanks collapsed, joined with one blank, the make left out when the model already begins with it as a whole word ignoring case), stored in the sidecar like `date`. Positions (#112): `ImagePart.location` is an optional `GeoLocation{latitude, longitude}` in decimal degrees, read once at analysis from the EXIF GPS IFD (`GpsDirectory.getGeoLocation()`, which applies the N/S/E/W reference letters and also answers an mp4 or QuickTime container's own position) and **stored in the sidecar** like `camera` — absent means the file says nowhere, `0/0` stays a real place, and a part a sidecar already lists is never analysed again; it follows the image's own privacy level and nothing besides, so whoever may see the image is answered its position (`PrivacyFilter` unchanged). Video dates (#72, #102): a video is dated by the `mvhd` creation time of its container, and a time before `ImageData.EARLIEST_RECORDING` (1990-01-01 UTC) is no recording time; the chain then asks the **file name** — `ImageData.nameDate` reads `YYYYMMDD[_- ]HHMMSS…`, `YYYY-MM-DD[ at |_| |T]HH[.:-]MM[.:-]SS` or a bare day (midnight) in the default zone, plausible only for a year in 1990…next year and a real day and time, the rule pinned for both toolchains by `image-server/src/test/fixtures/name-dates.json` — and only then does the file's modification time stand; `AlbumUtil.insertSorted` never resorts what a sidecar already lists. Dates and placement (#48): `AlbumInfo.date` is stored, `effectiveDate` is derived on read by `AlbumDate` (explicit → folder-name date → earliest image date) and cleared before any sidecar write; `ListingInfo.placement` (`NONE|BY_YEAR|BY_YEAR_MONTH`) is applied by `PlacementRule` on creation, on a move into the folder, and by `POST <folder>/?action=place`. Folder names (#130): a folder's name on disk is derived from its properties and the server keeps it so — `FolderNames.of` composes `yyyy-MM-dd title` for an album (`FolderNames.albumFolderName`, the Java twin of `valbum_ui/lib/album_date.dart`'s `albumFolderName`, both pinned by the shared table `image-server/src/test/fixtures/folder-names.json`) and the title alone for a folder of folders, and **every** sidecar PUT of an existing folder renames the directory to it before writing (`MoveService.renameFolder`, a same-filesystem rename: sidecar, `.hashes.json` and `.vacache` ride along, `ShareStore.rename` rewrites the `path` of every link on the folder and below it). The answer is always a `CreateResult{path, message}` — where it is now, and `FolderNames.renamedTo(...)` when it moved — which the app follows (`showPath`) and says in a snack bar. A name a sibling holds → 409 `nameTaken`, a title composing to no legal name (`.`, `..`, leading `.`, `/`) → 400, **nothing written** in either case. Never renamed: the space root, a year/month folder, and a folder whose properties compose nothing (no title). An album with no explicit date **keeps the date text its name carries** (`AlbumDate.leadingDateText`), so the folder-name date stays the fallback it is (`AlbumDate` unchanged) and writing a description never undates an album; a rename never *places* the album, so a changed date does not file it into another year folder. The date is shown where the album is named (#107): `albumDateLabel` (`valbum_ui/lib/album_date.dart`) writes `effectiveDate` out in the locale's medium form (`DateFormat.yMMMd()`) and answers `null` for `0`, and that one line stands between the title and the subtitle of a listing tile (key `folder-date`) and under the album's own heading (key `album-heading-date`, `album-date` being the properties dialog's field). **An album may have no date** (#119): the create dialog's date field is optional, the folder name is `albumFolderName(date, title)` — `yyyy-MM-dd title`, the title alone without a date, the one composition the move picker's `folderLine` uses too — and the dialog says "Without a date the album stays in this folder.", which is what the server does (`PlacementRule.placementFor` files nothing that has no date, pinned by `TestPlacement.testAnAlbumWithoutADateStaysWhereItWasAsked`); that is how an `Inbox` is made by hand.
- Spaces (#82, Phase 6): a server hosts one space or several. `Spaces.detect` decides the mode at start-up — **multi** as soon as one folder directly below the base folder carries `.valbum/space.json`, **single** otherwise; `--spaces auto|single|multi` overrides. `SpaceStore` reads `space.json` `{name, anonymous: none|public, mapUrl}` (missing/unknown values read closed; `mapUrl` is the #112 map template carrying `{lat}`/`{lon}`, `SpaceStore.DEFAULT_MAP_URL` = `https://www.google.com/maps?q={lat},{lon}` where the file names none or names a blank one, answered by `?type=auth` as `AuthInfo.mapUrl` — there is no provider enum, a provider *is* a template); a space is created on disk by hand, never by the server, and a new one is picked up by a restart. Each space has its **own** `AuthService` rooted at its own folder, so its `.valbum/users.json`, devices, invitations and albums are its own and a token of space A is simply unknown in space B (anonymous there). Anonymous access is a property of the space: `public` → the space runs like `--auth writes`, `none` → like `--auth all`; a server-wide `--auth all` is never loosened and `--auth off` stays off. Addressing in multi mode goes through `SpaceServlet` at the context root: `<context>/<space>/data/...` is that space's data root (the request is handed on with servlet path `/<space>/data`, so redirects, `Location.spell` and share URLs are spelled in the caller's coordinates), `<context>/<space>/` serves the app with `<base href>` rebased onto it (`ResourceServlet.setBaseSegments` + `WebRootResolver.singleSegmentBase`, the one-segment sibling of `/s/<token>/`), the app's own files are untouched; a session of a space lives **under** it — `<context>/<space>/s/<token>/` and `<context>/<space>/i/<token>/`, rebased by `WebRootResolver.spaceSessionBase` (the three-segment sibling of `/s/<token>/`), because the app opened there has to find a data root, and `ImageServlet.appUrl` derives that base from the request's own servlet path so a single-space server keeps spelling `<context>/s/<token>/` exactly as before; a session address at the context root of a multi-space server is refused with `SpaceServlet.sessionNeedsSpace`, and a first segment that is neither a space nor a file is answered `404` with an `ErrorInfo` (`SpaceServlet.noSuchSpace`). Single mode keeps every address it had. Bootstrap (#89, reversing #86's "a nameless admin only comes from an old library"): **every space has its admin from the moment it exists** — `AuthService`'s constructor writes a nameless `admin` (clearance `all`, `mayShare`, no devices) into a space without `users.json`; the seat is never empty, only unnamed, and in `--auth off` nothing is written. While that admin has **no device**, `Main.reportSpace` issues and prints one **seat code** per space (`AuthService.issueSeatCode(fixed)`: an ordinary `DeviceCodeStore` entry, `issuedBy = DeviceCodeStore.SERVER_ISSUER` (`"server"`, never a device id, so no issuer to die with), ten minutes, once): `This library: sign the administrator in with the code ABCD-EFGH (valid 10 minutes, once; restart the server for a new one).` A restart withdraws the earlier one and prints a new one — which is also the recovery when the last admin device is lost — and a space whose admin has a device prints nothing. `--admin-code <code>` fixes the code (validated by `DeviceCodeStore.checkCode`, alphabet and length, dashes ignored; the demo server uses `ABCD-EFGH`). Redeeming a code for a user **without a name** needs a non-blank `userName` — else 400 `NAME_REQUIRED` (generalising #86's `ADMIN_NAME_REQUIRED`) — and writes it on the user (`UserStore.checkUserName` + `isNameFree`, 409 `nameTaken`); for a named user the `userName` is a check as before (401 `DEVICE_CODE_OTHER_USER`). **`--pairing-secret` is retired**: given on the command line the server refuses to start (`Main.retiredSecret`, naming `--admin-code`), and a pairing carrying `PairRequest.secret` without a code answers 410 `SECRET_RETIRED` for one release; a pairing carrying nothing answers 400 `CODE_REQUIRED`. `AuthService.nameNamelessOwner(suggestion)` stays for a nameless admin **that has devices** (a library written before Phase 6, where nobody would ever be asked) — at start-up (`Main.reportSpace`, one printed line) or by `--migrate-to-spaces` (a report line) — the space's segment in multi mode, `owner` in single mode, with `-2`, `-3`… when a user or a top-level folder already holds it, and their devices and token hashes untouched, so every device keeps working. So a signed-in user always has a name and `Caller.subject()` never files their contribution as `anonymous`; every further user comes in through an invitation, which now carries `role`, `clearance` and `mayShare` (`Clearances` = `public|nonPrivate|all`, capped at the inviter's own), stored on the created user. `ImagePart`-style permission fields on the stored user (`clearance`, `mayShare` in `users.json`) and on `AuthInfo`/`UserEntry`/`Invitation` are written and answered here and enforced by #83. `?type=auth` names the space, the role, the clearance and the share flag. Migration is explicit: `--migrate-to-spaces` (like `--migrate-to-user`, refuses to start the server, rename-only, nothing deleted) turns an un-migrated library into the one space it already is (nothing moves) and a per-user library into a multi-space server — every user folder gets a `space.json` and a `users.json` holding that user as its admin with their devices, and `users.json`/`grants.json`/`groups.json`/`shares.json`/`invitations.json`/`device-codes.json`/`.valbum/guests/` plus every `.links.json` and `share-registry.json` in the tree are moved under `<base>/.valbum/retired/<timestamp>/` and named in a printed report saying what each held and what to do instead (`SpacesMigration`).
- Video renditions (#74): beside the poster frame, `VideoRenditions` (one per servlet, shut down in `ImageServlet.destroy()`) makes two sidecars per video in the album's `.vacache` — `video-<name>.mp4` (faststart, H.264 720 px short side, ≤30 fps, AAC) and `teaser-<name>.mp4` (~3 s from ~10 % in, silent, 240 px, faststart) — with the FFmpeg *program* of the bundled `org.bytedeco:ffmpeg` (`Loader.load(org.bytedeco.ffmpeg.ffmpeg.class)`), run as a child process with an argument list (never a command string), `-threads` at half the processors, one transcode at a time on a dedicated single-thread executor independent of the #69 preview permits. The encoder is chosen once by asking the program (`-encoders`): `libx264` if present, else `libopenh264` (what the LGPL build ships), else nothing is transcoded. `?type=video` / `?type=teaser` on an image path need `view` like the thumbnail and answer `video/mp4` over the existing range path; a rendition not yet made is never awaited — `202` + `ErrorInfo` `RENDITION_PENDING` + `Retry-After: 10` and the transcode is queued (deduplicated per rendition); a failed transcode is remembered for the process lifetime and answered `500` + `RENDITION_FAILED` with the FFmpeg tail in the log. Written to `.tmp` and moved atomically, invalidated like previews (`PreviewCache.LAST_UPDATE`); the original is never touched. The child process is started through `VideoRenditions.program(...)`, which sets `LD_LIBRARY_PATH` to the JavaCPP cache directory the program was extracted to, so the bundled libraries reach it on ARM too, where the program carries `DT_RUNPATH` (which the loader does not apply to indirect dependencies) rather than `DT_RPATH` (#87); what no platform jar ships — `libxcb1`, `libxcb-shm0`, `libxcb-shape0`, `libxcb-xfixes0` and ALSA — the Debian package recommends (`image-server/src/deb/control/control`, checked by `TestDebianPackageLibraries` against the ELF `DT_NEEDED` entries of the bundled artifacts).
- Preview generation (#69): `PreviewCache.createPreview` throttles only the *generation* of a preview — `--preview-threads <n>` / the system property `valbum.previewThreads` / `availableProcessors()` permits of a `Semaphore`, deliberately not a limit derived from free memory (the reasoning is in the Javadoc of `PreviewCache.permits`); serving a preview that is already cached takes no permit. A `ConcurrentHashMap` of in-flight futures keyed by the preview's absolute path makes concurrent requests for the same uncached file wait for the one generation and share its outcome (the same `PreviewException` for every waiter, the entry dropped so a later request may retry); the preview is written to `preview-<name>.tmp` in `.vacache` and moved into place with `ATOMIC_MOVE` (falling back to `REPLACE_EXISTING`), so nothing ever serves a half-written file. Refreshing (#98): `POST <folder>/?action=refresh-cache` (admin only, `AuthService.mayAdminister`, else 403 `CACHE_REFRESH_REFUSED`) deletes in that one folder's `.vacache` exactly what the server generated — `CacheRefresh.isGenerated`: `preview-*`, `video-*.mp4`, `teaser-*.mp4` and those under their `.tmp` name — never recursive, never a sidecar or an original, forgets the folder's failed-transcode memory (`VideoRenditions.forget`) and answers `CacheRefreshed{removed}`.
- Static web content: the server serves `META-INF/resources` of the class path (the Flutter web build, icons included, if `valbum_ui/build/web` existed at `package` time) at the context root; `--webroot <dir>` serves a directory from disk with precedence over the class path. Unknown paths without a file extension fall back to `index.html` (client-side deep links).
- Test fixtures live at `image-server/src/test/fixtures/test-album`.
- Java lint/format (Spotless, lightweight — tidies imports/whitespace, preserves tab indentation; **not** bound to a build phase): `mvn spotless:check` / `mvn spotless:apply`.

## Gotchas

- **Model classes are generated.** `image-server-shared/src/main/java/.../shared/model/model.proto` is the source of truth; the msgbuf-generator Maven plugin regenerates the model on every build. Edit the `.proto`, never the generated output. This generates **both** the Java model classes **and** the Dart file `valbum_ui/lib/resource.dart` (see the `option DartLib=...` line in `model.proto`) — `resource.dart` is generated, so don't hand-edit or reformat it.
- **Java 21** (`maven.compiler.release` in the root pom). The former 1.8 setting was a GWT constraint and is gone; a JDK 21 is required to build (the Maven enforcer checks it).

- Commit directly to `master` and push after every reviewed, gated change (see the `valbum-workflow` skill). Feature branches and PRs are for external contributors, not for the working session.
